# Forward-only migrations

1. Generated by the repo's migration tool, never hand-written SQL or edited journals.
2. Additive, so the previous release still runs against the new schema if the deploy rolls back.
3. No statements that scan or rewrite populated tables under a long lock. A change to existing rows gets its
   own guarded release.
4. Never write or propose a down-migration. Recovery is a snapshot restore.

Why: deploys roll back pods, not schema, and long locks on a live database cause outages.
